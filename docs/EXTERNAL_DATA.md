# External data sources

Eleven sources beside Djinni: what each one is, what it measured, what its labels mean, what can go wrong
with it, and what has to be settled before anything derived from it leaves the project. Every source was
downloaded (for PopResume, the code repository and its JDs; its gated CV files were only probed), profiled and
then independently verified on 2026-10-19. ConFit was downloaded in full but holds only placeholder text. Where
the verifier corrected the profile, the verifier's number is the one used here.

`src/hiring_bias_mitigation/data/external.py` is the registry: the roles, licences, held-out splits and the
`publishable` flag of each source live there, and this page explains them. Nothing here is vendored. The raw
downloads and the staged parquet live under `$HBM_EXTERNAL_ROOT` (default `$HBM_OUTPUT_ROOT/external_data`),
one directory per slug: `raw/`, `staged/`, `MANIFEST.json` (sha256 of every raw file) and `PROFILE.md`.

**Where each number comes from.** Numbers are tagged with their source.

| Tag | Source |
|---|---|
| [P] | the source's `PROFILE.md`, written by the agent that downloaded it, from the scripts in `_scripts/<slug>/` |
| [V] | the independent verifier's record for the source in `_acquire_verify_results.json` (`result.datasets[i].verify`), from the scripts in `_scripts/<slug>/verify/`. Corrections there override [P] |
| [O] | the cross-source overlap check, `_overlap/OVERLAP.md` and `_overlap/summary.json` |
| [M] | measured for this page through `data/external.py` on the staged files; the commands are under [Reproducing](#reproducing) |

Paths that start with a source slug, `_scripts/` or `_overlap/`, and `_acquire_verify_results.json`, are
relative to `$HBM_EXTERNAL_ROOT`; every other path is in this repository, with modules written as in CLAUDE.md
(`data/external.py` for `src/hiring_bias_mitigation/data/external.py`). A number marked "per paper", "per card"
or "per README" was read from that document and not measured.

## Why external data

The V1 training data (`artifacts/semisynthetic-v1`) has one source, the public mirrors of the Djinni
Recruitment Dataset (`generation/pool.py`, `data/PROVENANCE.md`): CVs and job descriptions from the Ukrainian
IT job market, in English and Ukrainian. The 450-pair benchmark was drawn from the same dataset, which is why
its holdout ids match the Djinni UUIDs directly. That leaves four things V1 cannot do.

- **Generalisation.** Training and evaluation share one market and one occupation family, so nothing tests
  whether a mitigation still holds on other occupations, other markets or other ways of signalling identity.
- **Human reference.** The benchmark's reference decision was generated by GPT-4o. No V1 number compares the
  model with a human matching judgement.
- **Qualification sensitivity.** Counterfactual set stability is maximised by a model that ignores the CV. V1
  has no pair that differs in qualification and nothing else, so it cannot show that a stable model still
  reads qualifications.
- **Occupational grounding.** The teacher decides without any occupation-level reference for what a job
  requires.

What the new sources can and cannot add, by registry role:

| Role (`ROLES`) | What it can answer here | Sources | What it cannot do |
|---|---|---|---|
| `train_pool` | more occupations and a second labour market (US) for teacher-decided pairs | RJDB train split, `kaggle_resume`, `resumeatlas` (CVs); `linkedin_postings` (JDs) | No source supplies a hire/reject decision, so the teacher still decides. All of them are English, so the Ukrainian side stays Djinni-only. None is attribute-free in the implicit sense without name and contact handling (cards below) |
| `eval_counterfactual` | does a mitigation trained on Djinni keep decisions stable under identity cues in another market and another cue style? | FAIRE (Name variants), LLMHiringFairnessSG, TalentCLEF siblings; PopResume when unblocked | None uses the benchmark's injection (a labelled field or a first-person sentence). The closest to a single-attribute set are FAIRE's gender Name pairs, which keep the surname and the whole body and change only the first name (98 of 98 [M]; 74 after the verifier's filters [V]); the other sets vary several cues at once. None varies military status. Religion appears only as a confound. Race and ethnicity, which they do vary, are not project attributes. None has hire/reject labels |
| `eval_reference` | does the model agree with human matching judgements? | TalentCLEF dev qrels, Vanetik-Kogan rankings; ConFit is blocked | TalentCLEF gives positives only, judged in English; Vanetik-Kogan's two annotators agree at chance. Neither is a hire/reject ground truth |
| `eval_qualification` | does a debiased model still prefer the stronger of two CVs of the same person? | RJDB dev and test | The weaker CV is a GPT-4 rewrite, not a deletion, so the pair differs in more than qualification |
| `rubric` | occupation-level priors for education, experience, skills and tasks; occupation tags for stratifying results | O*NET 31.0 | No CVs, JDs or decisions |

## Source cards

Training-pool sources first, then evaluation sources, then the rubric and the two blocked sources.

### `rjdb`: RJDB (Megagon Labs)

**What it is.** The Resume-Job Description Benchmark, Pezeshkpour, Iso, Lake, Bhutani and Hruschka (Megagon
Labs and Indeed), arXiv 2311.06383. It is fully synthetic English text. Per the README and paper, GPT-4
generated each record from a subgraph of a skill-occupation graph built from the DICE tech-job skill graph,
extended with 1,112 US BLS occupations and filtered with Indeed statistics. Each record is a triple: a JD, a
matched resume, and an unmatched resume that GPT-4 regenerated from the matched one "excluding" some skills,
with the most recent experience shortened or removed [P].

**Files and fields.** `dev.jsonl` and `test.jsonl` from the GitHub repo, `train.jsonl` from Google Drive [P].
Staged: `cvs` (matched rows `…-m` are bases; unmatched rows `…-u` point at them, and their `variant` encodes the
removed skills and the experience change), `jobs`, `pairs` (`label` match/mismatch,
`label_kind=synthetic_construction`). `extra` keeps the seed `Skills`, `Experiences`, `Experiences-years` and
the full `Filtered-information`. There is no native id, occupation code or label field; `occupation` is the
seed experience that best matches the parsed JD title [P].

**Measured.**
- Triples: train 50,000, dev 2,454, test 1,000 [M]. The paper says 52,000 split 50,000/1,000/1,000 [P].
- Matched CVs inside 400-6000 characters after strip: 50,518 of 53,454 [M]. Passing the pool's length and
  marker filters: 50,326 on stripped text, 50,488 on unstripped text as `pool.py` measures length [V].
- Median matched CV 685 characters [P]. 7,548 inferred occupations; about 39% of records have a BLS-style
  (mostly non-IT) occupation by a heuristic, since the BLS list could not be fetched [P,V].
- 0 exact or near-duplicate texts within or across splits [P,V]. Seeds repeat: 131 test and 345 dev records
  share a seed with train (130 and 313 distinct seeds) [V].

**Labels.** Match versus mismatch is implied by which field a text sits in. It is not a hire/reject decision
and not a human judgement; the README defines the unmatched resume as "a weaker match", and the paper's own
zero-shot setup uses maximally changed unmatched resumes as positives [V]. No human labels are released [V].

**How the unmatched CV differs** [P,V]:
- skills removed per triple: 0, 1, 2, 3 in 27, 20,304, 17,649 and 15,474 triples (mean 1.91);
- most recent experience shortened (54.2%), dropped (34.0%) or unchanged (11.8%);
- it is a rewrite: 6,270 of 53,454 (11.7%) unmatched CVs are line-subsets of the matched CV ignoring year
  lines [V], and 1,811 (3.4%) are strict line-subsets after whitespace normalisation [M]. The full name
  differs in 15.4% of parsed pairs, and 11,706 (21.9%) still mention a "removed" skill [V].

**Risks.**
- Names: the `Name:` field parses in 90.7% of matched CVs [P]; per the paper the names were sampled to balance
  gender and race, and the files carry no gender or race label. Emails are mostly derived from the name, and
  13,501 matched CVs (25%) use an address at a real consumer provider [V]. `_MARKERS` catches neither.
- Generation artefacts: leaked `######` delimiters in 1,514 texts, a stray trailing `#` on 4,500 JDs and 4,506
  matched CVs, model notes and placeholders [P].
- Matched pairs are near-trivial fits: 88.4% of seed skills appear literally in the JD [V].
- 193 matched CVs hit `_MARKERS`, mostly false positives (occupational uses, the first name "Christian"), a few
  genuine military or religion cues [P,V].

**Use here.** Train split as training-pool text (the teacher decides). Dev and test held out
(`holdout_splits=("dev", "test")`) as the qualification-sensitivity control: on each triple, a debiased model
should still prefer the matched CV. Read it as a pairwise check, not an accuracy, given the rewrite noise above.

Sources: `rjdb/PROFILE.md`, `rjdb/profile_stats.json`, `rjdb/profile_extra_checks.json`, `_scripts/rjdb/verify/`.

### `kaggle_resume`: Kaggle Resume Dataset (snehaanbhawal)

**What it is.** 2,484 English, US-style resumes in 24 categories, Kaggle version 1 (2021-08-08) [P]. Per the
uploader's scraper notebook (read as text), they were scraped from livecareer.com's resume-search directory,
filtered to LiveCareer resume score 85-100, keeping only links marked `rel="ugc"` (user-generated content).
`Category` is the upper-cased search keyword, not the job the resume was used for [P,V].

**Files and fields.** `Resume/Resume.csv` (`ID`, `Resume_str`, `Resume_html`, `Category`) and one PDF per
resume, rendered from the HTML with pdfkit/wkhtmltopdf, so not an original document [V]. Staged `cvs`: `text` is
`Resume_str` stripped, `occupation` is `Category`, and `extra` keeps the LiveCareer headline (field `LNAM`),
the full HTML and the filter flags [P].

**Measured.**
- 2,484 CVs, 2,482 distinct texts [M]; 1,322 inside 400-6000 characters [M]. Whitespace is 18.7% of all
  characters, so collapsing it would bring 1,519 in range (not applied) [P].
- `_MARKERS` hits 359 CVs (14.45%), mostly military (185) and veteran/army (123) [P,V].
- Usable under the pool's length and marker filters: 1,165, and 1,162 after dropping near-duplicates [V].
- Near-duplicate pairs at word-5-gram Jaccard >= 0.8: 6 [V].

**Labels.** `Category` only. For about 8 categories (for example AGRICULTURE, APPAREL, BPO, ARTS, AVIATION)
it is not even a reliable occupation label: few headlines match their own category [P,V]. There are no JDs, no
pairs and no outcomes.

**Risks.**
- Provenance: LiveCareer users' content; the CC0 label is the uploader's declaration. LiveCareer's terms were
  not checked [P,V].
- PII remains in a minority of CVs: 19 with an email, 56 with a phone number, 99 with a URL (25 LinkedIn), 45
  with a date-of-birth field, 8 with a passport field [P,V].
- `_MARKERS` misses military branches: about 15-18 of the 1,165 usable CVs still disclose service through
  Navy, Air Force, Marine Corps or discharge wording [V].
- Heavily downloaded public corpus (81,048 downloads per the Kaggle API), so pretraining exposure is likely [V].
- LiveCareer family overlap: FAIRE built on this dataset. 97 of its CVs are FAIRE's base CVs, and 1 (Kaggle id
  `91635250`) is the CV that FAIRE row 19's Experience variants were rewritten from. It also shares 242
  near-duplicates with ResumeAtlas at the overlap rule (368 at a looser 0.5 level) [M,O]. See
  [Contamination](#contamination).

**Use here.** CV side of the training pool, paired with JDs from elsewhere, matching on the headline rather
than `Category`. Never an evaluation set. The external holdout flags all 98 of those CVs. It removes nothing:
`find_external_leaks` reports them and `assert_no_external_leakage` raises, so whatever builds the pool has to
drop them first.

Sources: `kaggle_resume/PROFILE.md` (with its verifier addendum), `kaggle_resume/profile_stats.json`,
`_scripts/kaggle_resume/verify/`.

### `resumeatlas`: ResumeAtlas

**What it is.** A resume-classification corpus (arXiv 2406.18125): 13,389 rows of `Category` and `Text`. Per
the README and paper, the text is OCR (Google Cloud Vision, per paper) of resume images from Bing image search,
Google image search and LiveCareer [P]. The HF copy is a preprocessed version (lowercased, punctuation and
stopwords removed); the staged text is the raw OCR from the GitHub Git-LFS `Dataset.csv` [P,V]. There is no
native id, no JD, no pair and no published split [P].

**Measured.**
- 13,389 CVs, 12,175 distinct texts [M]; 9,602 inside 400-6000 characters [M]. 43 categories [P,V].
- The file is three blocks in file order of 2,722, 3,015 and 7,652 rows, equal to the README's Bing, Google and
  LiveCareer counts. The LiveCareer block carries LiveCareer's placeholder contact data, the other two do not.
  The source names rest on the README and the count match; the Bing-before-Google order cannot be verified [V].
- `_MARKERS` hits 992 rows (7.41%) [P,V].
- The profile's filter cascade (length, markers, near-dedup at J >= 0.8, lorem-ipsum, pseudonym artefacts, poor
  OCR) leaves 7,494 rows: Bing 2,186, Google 2,331, LiveCareer 2,977 [P,V].

**Labels.** `Category` is a scrape-query label: 169 groups of identical texts carry different categories [P,V].
It is not a match judgement.

**Risks.**
- Names: LiveCareer replaced each owner's name with the female-coded pseudonym "Jessica Claire" (7,613 rows,
  case-insensitive), by a global substring swap that also corrupted ordinary words: 436 rows by the profile's
  regex, 449 by a broader one, so 436 is a lower bound. In
  the 7,494-row pool, about 79% of rows carry a name in the header (all LiveCareer rows the same pseudonym) [V].
- PII: 1,663 rows (all from the image-search blocks) contain a personal-webmail address; up to 1,633 of them
  show no placeholder signal and may hold real contact data (heuristic, not verified) [P,V]. 186 pool rows have
  date-of-birth, nationality, gender, father's-name, age, passport or caste fields that `_MARKERS` misses [V].
- Template content: 69 lorem-ipsum rows, 17 rows under 400 characters, many vendor sample resumes [P,V].
- Licence: see [Licences and terms](#licences-and-terms).
- Overlap with the LiveCareer family; the external holdout flags 14 rows, all matching FAIRE CVs [M,O].

**Use here.** CV side of the training pool after name and contact neutralisation, the extra demographic-field
scrub and cross-source deduplication. Never an evaluation set.

Sources: `resumeatlas/PROFILE.md`, `resumeatlas/derived/`, `_scripts/resumeatlas/verify/`.

### `linkedin_postings`: LinkedIn Job Postings 2023-2024 (Kaggle, arshkon)

**What it is.** Kaggle version 13 (2024-08-19): 123,849 LinkedIn job postings plus side tables (companies,
industries, job functions, benefits, salaries) [P]. Per the uploader's scraper repository (read as text), it was
collected with several logged-in LinkedIn accounts through LinkedIn's internal API. The card also thanks a
second person for scraping an additional 100,000 jobs, a collection that is not documented [V]. No CVs, no
applicants, no decisions.

**Files and fields.** Staged `jobs`: every posting with a non-empty description. `text` is the description,
`occupation` the LinkedIn job-function tags, and `extra` keeps every other posting column (company, salary,
location, URLs) plus industries, functions and the exact-duplicate group [P].

**Measured.**
- 123,842 JDs [M]; 104,534 inside 400-6000 characters [M].
- 98.5% were first listed in April 2024; 3 postings are from 2023 [P,V]. 95.1% have US-like locations [P].
- Duplicates: 16,084 exactly duplicated rows are removable [P,V]; at word-5-gram Jaccard >= 0.9, at least 29,896
  (24.1%) [V]; under the overlap rule (Jaccard >= 0.7 or containment >= 0.8), 38,149 (30.8%) [O]. About 78,800
  near-deduplicated clusters have a representative inside 400-6000, and about 51,800 if JDs hitting `_MARKERS`
  are also excluded [V].

**Labels.** None. `applies` and `views` are per-posting counters [P,V].

**Risks.**
- Terms: the CC BY-SA 4.0 label is the uploader's declaration over LinkedIn and employer content; LinkedIn's
  terms were not checked [P,V].
- Protected-attribute text: 50,664 JDs (40.9%) hit `_MARKERS`, mostly in equal-opportunity boilerplate
  [P,V]; 7,929 still hit after EEO-like sentences are removed [V]. Separate regexes (precision not audited)
  find job-relevant cues: veteran preference 1,015, security clearance 2,457, citizenship required 1,841,
  minimum age 4,762, religious employer 1,591 [V]. In such a JD the attribute can bear on the job, so a
  counterfactual on it no longer isolates bias.
- PII: emails in 16,322 JDs and phone numbers in 8,346, mostly recruiters; company names are kept in `extra` [P].
- Formatting: 41,794 descriptions have bullet lists glued into sentences by the scraper [V].
- The external holdout flags 2 postings (229 and 261 characters), each an equal-opportunity sentence contained
  in a held-out TalentCLEF or Vanetik-Kogan JD; both fall below the 400-character floor anyway [M,O].

**Use here.** JD side of the training pool, after deduplication and after excluding or tagging JDs with
job-relevant protected cues. Never an evaluation set.

Sources: `linkedin_postings/PROFILE.md`, `linkedin_postings/profile_stats.json`,
`_scripts/linkedin_postings/verify/`.

### `faire`: FAIRE

**What it is.** Wen, Patil, Saxena, Fu, O'Brien and Zhu, "FAIRE: Assessing Racial and Gender Bias in AI-Driven
Resume Evaluations", arXiv 2504.01420. One spreadsheet (`Resumes.xlsx`): per row a category, a JD and a base
CV, plus 14 perturbed CVs for 5 race groups and 2 gender groups, each as a "Name" and an "Experience" variant
[P]. The base CVs are Kaggle resume-dataset (LiveCareer) CVs; per the notebook (read as text, not run) the JDs
were generated by gpt-4o-mini from the CV itself and the Experience variants are gpt-4o rewrites [P,V].

**Files and fields.** Staged `cvs` (`variant` like `axis=race;…;type=name`, `extra.kaggle_match` holds the
recovered Kaggle id), `jobs` (98 paired JDs plus 2 orphan JDs with `split=orphan_no_cv`), `pairs` (98 base pairs,
`label` null). Variants reach their JD through `extra.job_id` [P,V].

**Measured.**
- 98 base rows with 97 distinct texts: rows 19 and 22 are the same CV [M]. 57 of 98 bases are inside 400-6000
  characters [M]. Eight categories have 10 rows; FINANCE and ENGINEERING have 9 [P,V].
- Name variants: 686, every one equal to a prepended name plus the base after whitespace normalisation [M].
- Experience variants: 686. 142 delete at least 20% of the base's content tokens and 29 are identical to the
  base after whitespace normalisation [M]. 63 lose at least 20% of the base's tail [V].
- `_MARKERS` hits 16 of 98 bases [P,V].

**Labels.** None. The paper scores CVs with LLMs on a 1-5 rubric and ranks them. There is no human judgement
[P,V].

**Risks.**
- Experience variants are not counterfactuals: they add identity-linked activities, change qualifications,
  inject religion (53 of the 98 White Experience variants), are often truncated, and two contain assistant
  chatter [P,V].
- Row 19's 7 Experience variants derive from a different Kaggle resume than its base, and keep that resume's
  real-looking name [P,V].
- Name variants are clean text edits. The gender pairs keep the surname and change only the first name (98 of 98
  [M]), but race-name sets mix genders, and first names are religion-coded in 26 of 98 White, 16 of 98 Asian
  and 10 of 98 male variants, against 0 of 98 female [V].
- Some bases state gender or religion outright, which a swapped name then contradicts; bases contain PII (dates
  of birth, a national id number, licence numbers, phone numbers, a LinkedIn URL), propagated to all variants [V].
- Each JD was written from its own CV, so every base pair is a tailored match, a likely "hire" ceiling [P].
- The paper's scoring truncated every resume to 3,250 characters, so its published effects are not comparable
  to full-text runs [V].
- After dropping the 16 marker bases, row 19 and the religion-coded names, 74 gender pairs and 48 race 5-sets
  remain; 47 and 31 of them have a base inside 400-6000 characters [V].

**Use here.** External counterfactual evaluation on the filtered Name variants only, held out entirely
(`holdout_splits=None`). Experience variants, if used, are reported separately as identity-linked content
probes. Stability is computed within the named variants, because the base has no name at all [V].

Sources: `faire/PROFILE.md`, `faire/stats.json`, `faire/strict_classes.json`, `_scripts/faire/verify/`.

### `llmhiringfairness_sg`: LLMHiringFairnessSG

**What it is.** Tan et al., "Small Changes, Big Impact: Demographic Bias in LLM-Based Hiring Through Subtle
Sociocultural Markers in Anonymised Resumes", arXiv 2603.05189v3 (Social-AI-Studio). 100 real Singapore job
ads, 20 occupations x 5, scraped from MyCareersFuture (64), Indeed (18), LinkedIn (13) and Careers@Gov (5). For
each ad, one neutral CV generated by an LLM (gemini-2.5-pro per paper) and written to be slightly
under-qualified. Each neutral CV has 40 variants: 4 ethnicities (Chinese, Malay, Indian, Caucasian; the files
say `tamil` for Indian) x 2 genders x 5 cue sets, each the neutral text plus an appended "Additional
Information" block of Languages, Activities, Volunteering and Hobbies [P,V]. The CVs carry placeholders
instead of names and contact data [P].

**Files and fields.** Staged `cvs` (100 bases + 4,000 variants; `variant` names ethnicity, gender and cue
index), `jobs` (a rendering of the authors' structured JD; the original scraped columns are in `extra`), `pairs`
(100 base pairs, `label` null). Outside the contract tables: `cvs_ablated.parquet` (20,500 cue-field
ablations), `cvs_v1_templates.parquet` (100 earlier synthetic CVs, a different set), `variant_diffs.parquet`,
`cue_inventory.parquet` [P].

**Measured.**
- 4,000 of 4,000 variants start with their base text exactly [M]; 100 of 100 bases are inside 400-6000
  characters [M]. The 40 cue sets are reused verbatim in all 100 jobs [P,V].
- `_MARKERS`: 0 of 100 bases; 200 of 4,000 variants (one cue set says "military", one says "female") [P,V].

**Labels.** None. The original tasks are pairwise comparison against the neutral CV (A/B/Tie), a 1-100 score,
shortlisting by top score, and demographic recoverability. No hire/reject prompt or label exists [P,V].

**Risks.**
- The appended block is not an attribute-only cue. 11 of 40 cue sets carry leadership titles (regex) and 26 of
  40 were judged experience-bearing; Caucasian variants always list 3 languages, most others 2 [P,V].
- Each cue tuple belongs to one basket, so two variants of one base always differ in all four fields and gender
  cannot be isolated. The language-only ablation level is the only ethnicity-only subset (98 jobs) [V].
- Religion is entangled with ethnicity: 8 cue sets (800 variants) name mosques, temples or festivals, none caught
  by `_MARKERS`. 5 cue sets (500 variants) contain explicit gender words; up to 5 contain uniformed-group or
  military-adjacent cues [P,V].
- The neutral CV lacks the block entirely, so variant-versus-neutral comparisons also compare length [P].
- JDs `job_007` and `job_008` are identical; the ablation files leak cue fields for `job_045` and `job_061` at
  levels 0-3 [P,V]. The generation and injection code, the paper's v2 templates, model outputs and the
  human-study data are not released [P,V].

**Use here.** External counterfactual evaluation, held out entirely. Set stability over the 40 variants per job,
reported separately for identity-only and experience-bearing cue sets and with and without the religion and
uniformed-group sets, plus the language-only ablation as the cleanest ethnicity-only set [V].

Sources: `llmhiringfairness_sg/PROFILE.md`, `llmhiringfairness_sg/staged/_profile_stats.json`,
`_scripts/llmhiringfairness_sg/verify/`.

### `talentclef2026_a`: TalentCLEF 2026 Task A

**What it is.** A CLEF 2026 shared task on job-person matching, built by Avature with UNED (Zenodo record
19652670, version 0.3.0). Per the overview paper: English CVs generated by LLMs from internal records, each
filled in as a male and a female profile with a sampled place of origin; JDs generated by gpt-5-nano;
everything translated into Spanish; human experts annotated the English data and the Spanish labels were
copied [P]. A system ranks the CV pool for each JD.

**Files and fields.** Staged `cvs` (per language: 472 dev and 476 test CVs; the corpus is entirely sibling
pairs, and the member with the lower raw id is designated the base), `jobs` (per language: 10 dev and 40 test),
`pairs` (dev qrels, `label="1"`, `label_kind=human_relevance`). `extra` holds the sibling link, the EN-ES
alignment and a gender inferred by the acquirer from Spanish morphology [P].

**Measured.**
- 1,896 CVs (948 bases, 948 siblings), 100 JDs, 944 dev pairs [M]; 891 of 948 bases inside 400-6000 [M].
- All 474 EN sibling pairs differ beyond the first six lines (the name and contact header) [M]. Inferred gender
  of the sibling: female 233, male 229, undetermined 12 [M].
- Dev qrels: 472 rows per language, all positive, over 420 distinct CVs; 52 CVs are positive for no JD [P,V].

**Labels.** Binary relevance, positives only, for 10 dev JDs; unlisted pairs are unjudged, not negatives. 8 of
45 dev JD pairs share positive CVs (for example a cashier and a sales director role), so relevance means "could
do this job", not "same occupation" [P]. Test qrels are not released [P,V].

**Risks.**
- Siblings are not single-attribute counterfactuals. Besides gender they differ in name, origin, employers,
  schools and cities in 474 of 474 EN pairs, in languages spoken in 214 of 474 (three test JDs ask for language
  skills), and in a religion-coded institution present in only one sibling in 4 pairs [V].
- Gender labels are inferred, and some names contradict them [V]. The designated base flips between languages
  for 251 of the 474 underlying pairs, so joins across languages must use the alignment, not `base_cv_id` [V].
- Every CV opens with a name and contact header that encodes gender and origin. 95 EN CVs use real webmail
  domains and some name real employer brands [V]. Names repeat heavily (242 distinct names in 472 dev EN CVs)
  [P].
- 11 of the 50 JDs map to SOC major group 15 (computer and mathematical) [V].
- LLM-generated text (Claude, GPT models per paper) [P].

**Use here.** External evaluation as a multi-attribute name/origin-swap robustness set, and the dev qrels as a
small human-positive matching reference; held out entirely. A decision flip between siblings cannot be
attributed to gender alone [V].

Sources: `talentclef2026_a/PROFILE.md`, `talentclef2026_a/staged/_stats.json`, `_scripts/talentclef2026_a/verify/`.

### `vanetik_kogan`: Vacancy-Resume Matching (Vanetik and Kogan)

**What it is.** Data accompanying Vanetik and Kogan, "Job Vacancy Ranking with Sentence Embeddings, Keywords,
and Named Entities", *Information* 14(8):468, 2023. 65 CVs as Word files, which per the abstract come from a
public Telegram channel for Israeli hi-tech job applications; 5 software-developer vacancies (from data.world,
per README); and two annotators' rankings of the 5 vacancies for CVs 1-30 [P].

**Files and fields.** Staged `cvs` (`split` annotated or unannotated), `jobs`, `pairs` (`label` like
`a1=2;a2=3`, the rank of the vacancy for the CV from each annotator; `extra` keeps both array readings) [P,V].

**Measured.**
- 65 CVs (30 annotated, 35 not), 5 JDs, 150 pairs [M]. All 65 CVs inside 400-6000 characters, 4 of 5 JDs [M].
- 10 pairs (2 CVs) come from an annotator array that is not a permutation [M].
- Agreement over the 28 valid CVs, under the two possible readings of the arrays: top-1 Cohen's kappa -0.013
  and -0.077, pairwise concordance 0.568 and 0.546 against a chance level of 0.5 [P,V].

**Labels.** Relative ranks of 5 similar vacancies for one CV, the job-recommendation direction. Not hire/reject,
and rank 5 does not mean unsuitable. The array semantics are ambiguous, and the annotation file was changed in a
commit of 2026-01-21, after the paper [P,V].

- PII and consent: full names remain in the text of 7 CVs, a date of birth or age in 8, immigration or
  citizenship statements in at least 8; the raw Word metadata names authors, including two CVs whose text is
  masked. Consent is not documented [V]. Do not quote these CVs anywhere.
- 51 of the 52 CVs numbered 14-65 were regenerated with python-docx and stripped to ASCII, which broke words
  [V]. CVs 3/19 and 51/53 are near-duplicates of the same person [V,O]. At least 6 CVs are not developer roles
  [V]. Two of the 5 JDs carry equal-opportunity text that hits `_MARKERS` [V].

**Use here.** A sanity check at most, held out entirely; the ranks are too noisy to anchor a metric.

Sources: `vanetik_kogan/PROFILE.md`, `vanetik_kogan/stats.json`, `_scripts/vanetik_kogan/verify/`.

### `onet`: O*NET 31.0 Database

**What it is.** The US Department of Labor/ETA occupational database, release 31.0 (August 2026), one record
per O*NET-SOC occupation with ratings of skills, knowledge, education, training and experience, Job Zone,
tasks, software and lay job titles [P,V]. Release 30.3 renamed or split several files (Skills became Essential
plus Transferable Skills; Technology Skills became Software Skills; Alternate Titles became Job Titles), and the
four-level Job Zone scheme dates from 30.2 [P,V].

**Files and fields.** Staged outside the CV/JD/pair contract (the registry lists `staged=()`):
`occupations.parquet` (1,016 rows: code, title, description, Job Zone, task counts, SOC 2018 prefix) and
`job_titles.parquet` (63,474 rows [M], 55,283 unique code-title pairs [V]).

**Measured** [P,V]. 1,016 codes, 867 of them SOC-level; 923 have tasks and a Job Zone, and the other 93
(residual "All Other" codes and 19 military-specific codes) have neither. Job Zone values are 2 (zones 1 and 2
merged), 3, 4 and 5.

**Labels.** None at the CV or JD level: the ratings are occupation-level averages, a prior rather than the
requirements of any vacancy [P].

**Risks.**
- US-only and English-only [V].
- Naive title matching fails on IT jargon: of the benchmark's 30 job positions, 13 score 100 against an O*NET
  title by fuzzy matching, 5 of those 13 tie across several codes, and several IT titles map to unrelated
  occupations [V].
- O*NET text carries protected cues (religion and military occupations); in those occupations the attribute
  bears on qualification, so they should be kept out of counterfactual generation [V].
- `_MARKERS` catches 9 of the 620 job titles of the military-specific occupations [V], so the pool's
  "attribute-free" filter misses most military-service wording. The same list is a ready lexicon for extending it.

**Use here.** Rubric only: occupation-level qualification priors for the teacher, occupation tags (SOC major
group, Job Zone) for stratifying results, and the military-title lexicon. It is the only source with
`publishable=True`, under the attribution conditions below.

Sources: `onet/PROFILE.md`, `onet/staged/_stats.json`, `_scripts/onet/verify/`.

ternary (1, 0, -1) in the rank files, where 90-99% of candidates are -1. How `satisfied` was produced is not
documented, and augmented pairs copy their base pair's label [V].

**Use here.** None as released. Unblock steps are under [Blocked or incomplete](#blocked-or-incomplete).

## Contamination

**The benchmark is clean.** No staged CV or JD is an exact or near duplicate of any of the 150 English
benchmark CVs or 171 benchmark JDs, by MinHash LSH and by exhaustive brute force over 164,451 CV items and
178,793 JD items [O]. The closest JD neighbour is a LinkedIn posting (`3903493943`) sharing Android-developer
boilerplate with one benchmark JD: Jaccard 0.2436, containment 0.4368 [O]. The external holdout scores it 0.437
(38 shared shingles), below its 0.5 threshold [M]. The LinkedIn verifier also found template-level overlap
between that benchmark JD and another posting (`3902839754`, 61.7% of the benchmark JD's word 8-grams; one
employer appears in both sets), and no same-posting overlap [V]. Not covered: paraphrases and translations,
`reference_feedback_uk.csv`, and the Djinni pool itself, which `pool.py`'s id-based holdout handles [O].

**The LiveCareer family overlaps.** `kaggle_resume`, FAIRE (whose bases are Kaggle CVs) and ResumeAtlas's
LiveCareer block share resumes [O]:
- all 98 FAIRE base rows are Kaggle CVs (96 normalised-exact); 1,077 of the 1,372 FAIRE variants are
  near-duplicates of a Kaggle CV;
- 242 Kaggle CVs are near-duplicates of ResumeAtlas rows, all in its LiveCareer block; at a looser 0.5 level,
  368 Kaggle CVs and 400 ResumeAtlas rows. OCR noise lowers n-gram overlap, so deduplicate this family with
  `_overlap/livecareer_loose_pairs.csv`, not only the main-rule pairs.

No other pair of sources shares a CV. Among JDs, the only cross-source matches are O*NET occupation
descriptions quoted inside 14 LinkedIn postings and 9 RJDB JDs [O].

**Counterfactual families are split by `base_cv_id`.** Text similarity does not keep siblings together: 95.2% of
RJDB unmatched CVs, 44.3% of TalentCLEF siblings and 18.6% of FAIRE variants fall below the near-duplicate rule
against their own base [O]. Any split of a counterfactual source therefore has to be by family id. The EN and
ES copies of a TalentCLEF CV are translations, invisible to n-gram matching, so they belong on the same side too
(recommended in [O], not checked there).

**The external holdout** (`data/external.py`). Ids cannot protect the external evaluation sets, because the
sources share no id space. The guard is on text:

- `holdout_index(kind)` indexes every held-out CV (`kind="cv"`) or JD (`"jd"`) of every source whose
  `holdout_splits` is set, plus the English benchmark: FAIRE, LLMHiringFairnessSG, TalentCLEF and Vanetik-Kogan
  in full, PopResume's JDs, RJDB dev and test. Only the tables a source lists in its registry `staged` field are
  read, and PopResume lists only `jobs`, so its CVs are not indexed. On the current staged data that is 14,589
  CV texts (RJDB 6,908, LLMHiringFairnessSG 4,100, TalentCLEF 1,896, FAIRE 1,470, benchmark 150, Vanetik-Kogan
  65) and 3,935 JD texts (RJDB 3,454, benchmark 171, FAIRE, LLMHiringFairnessSG and TalentCLEF 100 each,
  Vanetik-Kogan 5, PopResume 5) [M].
- Texts are normalised as in the overlap check (NFKD, accents dropped, lowercase, non-alphanumerics deleted,
  NLTK English stopwords dropped) and shingled into word 5-grams. A training text matches when
  max(Jaccard, containment either way) is at least `LEAK_THRESHOLD = 0.5` and at least
  `MIN_SHARED_SHINGLES = 10` shingles are shared. The overlap check's own rule is stricter (Jaccard 0.7 or
  containment 0.8); the guard is looser on purpose, because a false positive costs one training text and a false
  negative contaminates an external evaluation.
- `assert_no_external_leakage` raises on any match. `holdout_index` fails closed for the tables the registry
  lists: a held-out source whose listed staged table is missing raises `FileNotFoundError` rather than indexing
  nothing [M]. A blocked source that is not on disk is skipped with a warning. A table on disk that the registry
  does not list is ignored without a warning: with a `popresume/staged/cvs.parquet` added beside the real staged
  data, the CV index still holds no PopResume text, and an exact copy of that CV is not flagged [M].

What it flags on the training-pool candidates as staged today [M]:

| Candidate | Checked | Flagged | Matched held-out source |
|---|---:|---:|---|
| `kaggle_resume` CVs | 2,484 | 98 | FAIRE: 97 are the base CVs, 1 (Kaggle id `91635250`) is the source of row 19's Experience variants |
| `resumeatlas` CVs | 13,389 | 14 | FAIRE; the same 14 rows the overlap check pairs with FAIRE at its loose level [O] |
| `rjdb` train CVs | 100,000 | 23 | RJDB dev/test matched CVs, 7 distinct, scores 0.50-0.64. All 23 are matched (base) CVs; one (`rjdb-train-16130-m`) shares its seed and occupation with its match, the other 22 share neither |
| `rjdb` train JDs | 50,000 | 0 | |
| `linkedin_postings` JDs | 123,842 | 2 | one TalentCLEF and one Vanetik-Kogan JD; both postings are an equal-opportunity sentence under 400 characters |

Limits of the guard, as implemented:
- It reads only the contract tables. LLMHiringFairnessSG's `cvs_ablated.parquet` is not indexed but every row is
  a near-copy of an indexed base or variant [O]. `cvs_v1_templates.parquet` (100 separate synthetic CVs) is not
  indexed and matches nothing indexed [O], so a copy of a v1 template in training would pass.
- PopResume's CVs are outside it until its registry entry lists `cvs` in `staged`; running the stager alone
  does not change that (see the unblock steps under [Blocked or incomplete](#blocked-or-incomplete)).
- The normaliser keeps only `[a-z0-9]` after NFKD, so Cyrillic text yields no shingles [M]. The guard indexes
  the English benchmark only; the Ukrainian side relies on `holdout_ids.json`, as before.
- Like the overlap check, it cannot see paraphrases or translations.

## Blocked or incomplete

None of these steps was attempted; each needs the user's own account, request or decision.

- **PopResume CVs** (`popresume`). The HF dataset is gated with manual approval [P,V]. To unblock: sign in to
  Hugging Face, request access at `https://huggingface.co/datasets/sumin-yu/PopResume` (this shares the
  account's contact information with the authors) and wait for approval; create a read token and export it as
  `HF_TOKEN`; download only the text configuration (about 12.8 MB, not the 15.9 GB of images) with
  `hf download sumin-yu/PopResume --repo-type dataset --include "data/text/*" "README.md"`; then run
  `_scripts/popresume/stage_popresume_text.py` and re-check the sha256 values against the HF tree. The full
  commands are in `popresume/PROFILE.md`. The stager is untested on real data [V]. Before any training pool is
  checked against the staged CVs, the `popresume` entry in `data/external.py` has to list `cvs` in `staged`
  (today `staged=("jobs",)`); otherwise the external holdout ignores the CVs without a warning
  ([Contamination](#contamination)). While `blocked=True` stays set, a missing `cvs.parquet` is skipped with a
  warning instead of raising.
- **ConFit / IntelliPro** (`confit`). The public release holds placeholders only. IntelliPro text has to be
  requested from the authors (the README says "contact us directly" and gives no address); AliTianChi would need
  the original Tianchi competition data under its own terms [P,V].
- **TalentCLEF test qrels.** Not released. Ask the organisers (`machinelearning@avature.net`, per paper) or
  submit runs to Codabench competition 14226 if that is acceptable; official gender labels for the siblings would
  also come from the organisers [P].
- **BLS occupation list for RJDB.** `bls.gov/oes` returned HTTP 403 to scripted access, so RJDB's BLS-versus-DICE
  occupation split rests on a heuristic. Download the OES/SOC title list in a browser and place it under
  `rjdb/raw/` to replace the heuristic with exact matching [P].
- **Smaller gaps.** The Vanetik-Kogan paper (MDPI blocks scripted access) is needed to settle the annotation
  array semantics [P]. ResumeAtlas's original images need a Kaggle account [P]. A LICENSE file for FAIRE would
  have to come from its authors [P].
